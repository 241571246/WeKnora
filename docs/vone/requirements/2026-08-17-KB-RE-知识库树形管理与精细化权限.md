## 2. 背景与问题

当前 WeKnora 0.7.2 Standard 的知识库管理不能满足工作空间内按员工分配、共同所有、只允许 AI 使用、限制文件及切片预览，以及按项目树组织多个知识库的业务要求。

本需求需同时解决两个相互关联的问题：

1. 知识库的所有权、成员协作和能力级授权必须由后端强制执行，不能只依赖前端隐藏按钮。
2. 工作空间中的多个知识库需要按照“总项目—子系统—知识库内部目录”的层级进行导航和管理，同时不能混淆项目树与知识库内部文件目录。

## 3. 目标

1. 员工可以创建自己的知识库，并自动成为该库所有者。
2. 知识库所有者可以添加其他员工为共同所有者或其他权限角色。
3. Workspace Owner 可以创建多个知识库，分别授权给指定员工，并精确控制其管理、查看和 AI 使用能力。
4. 普通员工只能发现自己拥有或被授权的知识库及相应树节点。
5. 支持按项目/产品树组织多个知识库，并保留每个知识库现有的文件夹与文件层级。
6. 存量知识库能够安全迁移到新权限模型，且定制代码保持可持续合并上游主版本。

## 4. 角色定义

| 角色 | 定义 |
|---|---|
| Workspace Owner | 本需求中的“管理员”，拥有工作空间级治理和授权能力 |
| Knowledge Base Owner | 知识库所有者，可由创建者或被提升的共同所有者担任 |
| Editor | 按授权编辑知识库内容，但不默认拥有所有者及成员管理能力 |
| Document Viewer | 可查看授权知识库的文件清单、全文或切片，具体由能力项决定 |
| AI User | 只使用该知识库进行 AI 检索和问答，不进入知识内容管理界面 |

约束：知识库至少保留一名 Owner，系统不得移除最后一名 Owner。知识库 Owner 可以把其他员工设置为共同 Owner。

## 5. 功能范围

### 5.1 知识库创建、归属与可见性

1. Workspace Owner 和具备创建资格的员工均可自助创建知识库。
2. 创建成功后，创建者自动成为 Knowledge Base Owner，拥有该库最高权限。
3. 普通员工仅能看到下列知识库：
   - 自己为 Owner 的知识库；
   - 自己被明确授予任一权限的知识库。
4. Workspace Owner 可查看和治理当前工作空间全部知识库。
5. 未授权知识库不得通过列表、搜索、URL 猜测、接口枚举或 Agent 配置间接暴露。

### 5.2 成员与共同所有者

1. Knowledge Base Owner 可添加、移除知识库成员，调整成员角色或自定义能力。
2. Knowledge Base Owner 可将其他员工提升为共同 Owner。
3. 共同 Owner 具备与其他 Owner 等价的库级管理权限。
4. 移除或降级 Owner 前必须校验剩余 Owner 数量；最后一名 Owner 不可被移除或降级。
5. Workspace Owner 可对任意知识库执行成员治理和所有权纠正。

### 5.3 权限能力模型

系统至少支持以下独立能力，不得将“查看”“编辑”“删除”合并成单一开关：

| 能力编码 | 能力说明 |
|---|---|
| `kb.ai.query` | 使用知识库进行 AI 搜索、问答 |
| `kb.metadata.read` | 查看知识库名称、描述等基础信息 |
| `kb.documents.list` | 查看文件清单 |
| `kb.document.preview` | 预览文件全文 |
| `kb.chunk.preview` | 预览切片内容 |
| `kb.document.download` | 下载原文件 |
| `kb.document.upload` | 上传文件 |
| `kb.document.edit` | 编辑文件元数据或内容 |
| `kb.document.delete` | 删除文件 |
| `kb.document.reparse` | 重新解析文件 |
| `kb.chunk.edit` | 编辑切片 |
| `kb.chunk.delete` | 删除切片 |
| `kb.folder.manage` | 管理知识库内部文件夹及移动文件 |
| `kb.settings.edit` | 修改知识库配置 |
| `kb.delete` | 删除整个知识库 |
| `kb.members.manage` | 管理普通成员与权限 |
| `kb.owners.manage` | 添加、提升、降级或移除共同 Owner |

系统提供 Owner、Editor、Document Viewer、AI User 四个预设角色，并支持以自定义权限逐项开关。预设角色只是能力集合，不得替代后端能力校验。

### 5.4 AI User 的边界

1. AI User 默认仅具备 `kb.ai.query` 和回答所需的最小元数据读取能力。
2. AI 回答允许展示文件名称、引用来源和与回答相关的原文片段。
3. AI User 不得因此获得文件列表、全文预览、原始切片浏览、文件下载、编辑或删除能力。
4. 回答引用接口只能返回本次回答所需的引用信息，不得复用内容管理接口绕过权限。

### 5.5 管理员分配场景

Workspace Owner 可创建多个知识库，并分别为指定员工配置下列任一权限组合：

1. 仅 AI 使用：可问答，可看回答引用，不可进入文件及切片管理。
2. 内容查看：可查看文件清单，并按配置允许全文、切片或下载。
3. 内容编辑：可上传、编辑、重新解析；删除文件、删除切片、删除知识库分别授权。
4. 库管理：可修改配置、管理成员或所有者；每项能力独立控制。

### 5.6 树形结构管理

采用以下三层语义：

```text
Workspace
└── 知识库集合/项目树
    ├── 02-产品与解决方案
    │   ├── VCOS-游轮运营管理系统（知识库）
    │   ├── CRS-票务系统（知识库）
    │   └── PMS-海轮管理系统（知识库）
    └── 未分类
        └── 其他知识库

知识库
└── 现有内部 folder_path
    ├── 产品资料
    ├── 解决方案
    ├── 客户案例
    ├── 销售支持
    └── 演示与培训资料
```

具体规则：

1. 知识库集合/项目树支持任意层级的新建、重命名、移动、排序和删除空节点。
2. 一个知识库在本期只能归属一个集合节点；允许归入“未分类”根节点。
3. 删除包含知识库或子节点的集合时，必须先移动其内容，不得级联删除知识库。
4. 项目树在本期仅用于导航和组织，不继承或覆盖知识库权限。
5. 普通员工只看到包含其可见知识库的树分支；无可见知识库的空分支不展示。
6. 知识库内部继续使用现有 `folder_path` 组织文件，不在本期增加文件夹级 ACL。
7. 本期不要求持久化空的知识库内部文件夹；预先创建无文件的目录模板不在范围内。

### 5.7 Agent 与多知识库使用

1. 复用现有 Agent 多知识库配置能力，不新增项目级统一 AI 搜索页面。
2. Agent 实际可检索知识库集合必须取以下交集：Agent 已配置知识库 ∩ 当前调用人具备 `kb.ai.query` 的知识库。
3. 用户权限被撤销后，Agent 不得继续使用缓存中的旧授权。

### 5.8 审计与安全

1. 所有知识库列表、详情、文件、全文、切片、下载、AI、Agent 和成员管理接口必须在后端执行授权校验。
2. 前端菜单和按钮隐藏仅用于交互优化，不作为安全控制。
3. 权限授予、撤销、所有者变更、文件删除、切片删除、知识库删除、下载、拒绝访问和树节点变更均写入审计日志。
4. 权限撤销后最多 5 秒内对新请求生效；缓存必须按用户、工作空间、知识库和权限版本隔离。
5. 跨工作空间访问、直接使用资源 ID 和批量接口均执行同等校验。

## 6. 数据迁移要求

1. 存量知识库统一归入“未分类”集合，保留现有内部 `folder_path`。
2. 存量知识库以当前 `creator_id` 对应用户作为初始 Owner。
3. `creator_id` 为空、无效或用户已不存在时，由 Workspace Owner 接管，禁止产生无 Owner 知识库。
4. 迁移前盘点现有 `kb_shares` 数据并形成明确映射：转换为新 ACL、临时保留或禁用；任何旧共享记录都不得绕过新权限模型。
5. 在旧共享记录尚未完成转换和核对前，不得直接开启强制 ACL 导致合法访问丢失，也不得保留旧逻辑形成越权旁路。
6. 迁移脚本必须可重复校验、记录影响行数，并提供恢复方案。

## 7. 非功能与升级兼容要求

1. 定制主体放在独立模块、命名空间和独立数据库迁移中；与上游原功能混合处只保留必要的薄接入点。
2. 不修改已经发布的上游迁移文件；定制表和字段使用独立、可追踪的迁移序列。
3. 建议分支流：`upstream/main` → `main` → `custom/kb-acl-<sha>` → `release/vone-<sha>`。
4. ACL 上线顺序：数据结构 → 后端影子校验但不拦截 → 数据回填 → 权限配置 → 前端 → 强制执行。
5. 回滚不得直接切回完全忽略 ACL 的旧后端，否则会恢复过宽可见性；必须提供保持访问收敛的兼容回滚版本或维护窗口方案。
6. 权限判定逻辑需集中复用，避免各接口自行解释角色造成漂移。

## 8. 明确不在本期范围

1. 文件夹、单文件或单切片级的成员授权。
2. 按部门、用户组或岗位批量授权。
3. 集合节点权限继承。
4. 同一知识库同时挂载到多个集合。
5. 独立的项目级跨库 AI 搜索页面。
6. 持久化没有任何文件的知识库内部空文件夹。
7. LDAP、AD 或其他外部 IAM 集成。

## 9. 验收标准

### 9.1 所有权与可见性

- **AC-01** 员工创建知识库后立即成为 Owner，并拥有该库全部能力。
- **AC-02** Owner 可增加共同 Owner；系统拒绝删除或降级最后一名 Owner。
- **AC-03** 普通员工的知识库列表、项目树、搜索结果和直达 URL 只暴露自己拥有或获授权的知识库。
- **AC-04** Workspace Owner 可以查看和治理工作空间全部知识库。

### 9.2 细粒度权限

- **AC-05** 文件删除、切片删除、整个知识库删除分别授权；只授予其中一项时，其他两项接口均返回无权限。
- **AC-06** 未授予全文、切片或下载能力的用户，即使知道资源 ID，也不能通过接口取得相应内容。
- **AC-07** Editor、Document Viewer、AI User 预设能映射到明确能力集合，自定义能力修改后立即按能力生效。
- **AC-08** 所有敏感接口均有后端授权测试，前端绕过不能获得额外权限。

### 9.3 AI 使用

- **AC-09** 仅有 `kb.ai.query` 的用户可以获得 AI 回答、文件名、来源和必要引用片段。
- **AC-10** 同一用户不能打开文件列表、全文、原始切片、下载或编辑接口。
- **AC-11** Agent 只能查询其配置知识库与调用人可用知识库的交集。
- **AC-12** 撤销 `kb.ai.query` 后 5 秒内，直接 AI 与 Agent 调用均不再使用该知识库。

### 9.4 树形管理

- **AC-13** Workspace Owner 可建立多级集合树，并创建、重命名、移动和排序节点。
- **AC-14** 每个知识库只能归属一个集合；未分配知识库显示在“未分类”。
- **AC-15** 非空集合不能被级联删除，必须先移动其中知识库和子节点。
- **AC-16** 普通员工只看到包含可见知识库的树分支；项目树不改变知识库授权结果。
- **AC-17** 现有知识库内部 `folder_path` 文件树继续可用，且不被误当作项目集合权限节点。

### 9.5 迁移、审计与升级

- **AC-18** 存量知识库按 `creator_id` 归属 Owner；无效创建者由 Workspace Owner 接管，迁移后无孤儿知识库。
- **AC-19** 存量库归入“未分类”，内部文件、切片和 `folder_path` 数量与迁移前核对一致。
- **AC-20** `kb_shares` 均有转换/保留/禁用结论，旧共享逻辑无法绕过新 ACL。
- **AC-21** 授权、撤销、所有者变更、三类删除、下载、拒绝访问和树变更均可查询审计记录。
- **AC-22** 定制数据库迁移可在全新环境和现有 0.7.2 数据环境执行；上游迁移文件保持不变。
- **AC-23** 完成一次上游版本合并演练，输出冲突清单、构建结果、权限回归结果和可执行回滚步骤。

## 11. 已确认决策

1. “管理员”特指 Workspace Owner。
2. 员工可以把其他员工设置为共同 Owner。
3. 删除文件、删除切片、删除知识库必须分别控制。
4. AI 回答允许显示文件名、引用来源和必要原文片段。
5. 存量知识库默认归当前创建者；创建者无效时由 Workspace Owner 接管。
6. 项目集合树第一期不做权限继承，知识库仍是授权边界。
