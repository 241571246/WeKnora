## Current Source Baseline and Gap Analysis

| Area | Existing reusable capability | Gap against REQ-2026-001 |
|---|---|---|
| Workspace RBAC | `tenant_members` has Owner/Admin/Contributor/Viewer; enforcement defaults on | It is workspace-wide and cannot grant different permissions per knowledge base and per employee |
| KB ownership | `knowledge_bases.creator_id`; creator or Admin may mutate | Only one creator; no co-owner membership and no last-owner invariant |
| KB visibility | tenant list plus creator Mine/Others filter; organization/Agent shared rows | Same-workspace users can still discover tenant KBs; no owner/assigned-only SQL visibility rule |
| Resource guards | `RequireOwnershipOrRole`, `KBAccessRead/Write`, route-level guards | Coarse read/write ladder; cannot separate list/fulltext/chunk/download/file delete/chunk delete/KB delete |
| Sharing | `kb_shares` grants an organization viewer/editor access | Sharing target is organization/tenant, not an employee; existing route can bypass a new user ACL unless centralized |
| Audit | durable member and RBAC denial audit exists | New grant/revoke/owner/three-delete/download/tree events need action codes and coverage |
| Internal folders | `Knowledge.FolderPath`, folder list/rename/move and `KbFolderTree.vue` | This is a document folder tree, not a workspace project/KB collection tree |
| Agent | `KBSelectionMode` supports all/selected/none and shared-Agent access | Runtime set is not intersected with caller-level `kb.ai.query` capability |
| Frontend | Vue 3, TDesign, Pinia, knowledge list/settings/share dialog | No collection navigation, member matrix, capability-driven route/action rendering or AI-only experience |
| Migration | numbered PostgreSQL and SQLite migrations through current checkout | Independent customization sequencing and legacy `kb_shares` mapping/rollback contract still need design |

结论：采用“扩展现有链路”的二次开发。保留现有工作空间 RBAC 作为工作空间入口和管理员上限，在知识库资源层新增统一的 `KBPolicyDecision`/Authorizer；所有知识库及子资源接口统一消费能力判定，避免在每条路由继续叠加角色判断。

## Proposed Technical Boundary

### Data objects

1. `vone_kb_memberships`：`tenant_id`、`knowledge_base_id`、`user_id`、`role`、`granted_by`、时间戳和软删除；唯一键为有效的 `(knowledge_base_id, user_id)`。
2. `vone_kb_member_capabilities`：`membership_id`、`capability_code`；用于自定义能力和预设角色展开，不把能力列表硬编码进前端。
3. `vone_kb_collections`：工作空间内任意层级集合，包含 `parent_id`、`name`、`sort_order`、`created_by`。
4. `vone_kb_collection_bindings`：一个知识库最多一个集合绑定；无绑定即“未分类”。使用独立绑定表，避免直接修改上游 `knowledge_bases` 表结构。
5. 权限缓存第一期优先直接查库或使用不超过 3 秒的版本化缓存，满足撤权 5 秒内生效；不得仅靠固定长 TTL。

### Authorization precedence

1. Workspace Owner 具备工作空间内治理覆盖能力，但仍写审计记录。
2. 当前工作空间用户按 `vone_kb_memberships` 的 Owner/预设角色/自定义能力判定。
3. 现有组织共享按统一 Authorizer 转换为受限能力集合，不能直接绕过用户级策略。
4. Shared Agent 只在当前请求上下文内授予 `kb.ai.query` 与最小引用能力，不自动授予文件列表、全文、切片或下载。
5. API Key 继续执行 capability 与 KB allow-list，但必须映射到同一知识库能力判定接口。
6. 任一链路无法确定调用人、工作空间、知识库或能力时默认拒绝。

### Proposed API surface

| Method and path | Purpose |
|---|---|
| `GET /knowledge-bases/:id/access` | 返回当前用户角色和有效 capabilities，供前端渲染 |
| `GET /knowledge-bases/:id/members` | 查看成员、角色与自定义能力 |
| `POST /knowledge-bases/:id/members` | 添加员工或共同 Owner |
| `PATCH /knowledge-bases/:id/members/:user_id` | 调整角色/能力；校验最后 Owner |
| `DELETE /knowledge-bases/:id/members/:user_id` | 移除成员；校验最后 Owner |
| `GET /knowledge-base-collections/tree` | 返回按调用人过滤后的集合树和知识库 |
| `POST /knowledge-base-collections` | 新建集合节点 |
| `PATCH /knowledge-base-collections/:id` | 重命名、移动或排序集合 |
| `DELETE /knowledge-base-collections/:id` | 只删除空节点 |
| `PUT /knowledge-bases/:id/collection` | 移动知识库或设为未分类 |

现有知识库、文件、全文、切片、下载、搜索和 Agent 接口不另开绕过路径，而是在既有路由接入统一能力校验。
